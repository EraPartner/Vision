### Correctness — dates & timezones

- [x] 🔺 **[R7-1] PDF-report period boundaries shift a day in UTC+ timezones** — `apps/node-backend/src/services/reports/dataFetcherPortfolio.js:42-62` (`periodToDateRange`) and `dataFetcherTax.js:41-75` (`periodToTaxContext`). For `rolling` periods both build a **local-midnight** Date (`new Date(y, m - months + 1, 1)`) and serialize it with **UTC** `toISOString().slice(0,10)`. In Belgium (UTC+1/+2) local midnight on the 1st is 22:00/23:00 UTC of the *previous day*, so a "rolling 12 months" report starting 2025-07-01 actually queries from **2025-06-30** — one extra day of dividends/fees/sells in every rolling report and tax report, at any time of day. The `ytd` endDate (`now.toISOString().slice(0,10)`) is additionally *yesterday* between 00:00 and 01:00/02:00 local. **Fix:** format with local getters — reuse `toAppDateString` from `src/lib/timezone.js` (or `toYmd` from `utils/portfolioMath.js`) for both `start` and `today`; never mix local Date construction with `toISOString()`. ✅ 2026-06-11
- [x] ⏫ **[R7-2] "Today" computed in UTC in five places — wrong day until 01:00/02:00 Belgian time** — `routes/info/_queryParams.js:30-32` (`getCurrentDateString`, default date for /api/info queries), `routes/plannedTransactions.js:130-132` (duplicate `getCurrentDateString`, default `execution_date` when executing a planned tx), `routes/info/_performanceHelpers.js:51-53` (period cutoff in `filterSnapshotsByPeriod`), `services/currency/rateFetcher.js:189`, and `services/reports/dataFetcherPortfolio.js:44`. All use `new Date().toISOString()`. Concrete symptom: executing a planned payment at 00:30 local stamps `last_executed_date` with *yesterday's* date, which also derails the next-occurrence advance and occurrence-keyed reminder dismissal (keyed `id:YYYY-MM-DD`). **Fix:** one shared `todayAppDateString()` in `src/lib/timezone.js` (it already has `toAppDateString(new Date())`); replace all five call sites; delete both local `getCurrentDateString` copies. ✅ 2026-06-11
- [x] 🔼 **[R7-3] Import-adapter date fallbacks parse local, serialize UTC → previous-day shift** — primary paths build `Date.UTC(...)` correctly, but the fallbacks parse with plain `new Date(string)` (local time for non-ISO formats): `importPipeline/adapters/vision.js:16`, `revolut.js:21` (generic fallback), `wise.js:51`, `sabb.js:27`, `generic.js:38`. Downstream `stage.js:83` and `deduplication.js:13,44` serialize via `toISOString()`, so any non-ISO date row imports with the previous day's date in UTC+ timezones — and the dedup hash changes with it (same row could import twice depending on server TZ). **Fix:** in `_shared.js`, add a strict multi-format parser that always constructs `Date.UTC` and returns null for unrecognized formats; remove the `new Date(string)` fallbacks. ✅ 2026-06-11
- [x] 🔽 **[R7-4] snapshotBuilder mixes DB `CURRENT_DATE` (UTC) with app-timezone walk end** — `services/portfolio/snapshotBuilder.js:78,94`: transaction/price queries are bounded by Postgres `CURRENT_DATE` (container TZ, UTC) while the day-walk ends at `toAppDateString(new Date())` (line 313, app TZ). Between 00:00–02:00 Belgian time the walk emits today's snapshot but the queries exclude today's transactions; self-corrects on the next rebuild, so impact is a transiently stale latest snapshot. **Fix:** pass `todayYmd` as the upper bound parameter instead of `CURRENT_DATE`. ✅ 2026-06-11

### Correctness — functionality & money math

- [x] 🔺 **[R7-5] FIFO/LIFO cost-basis setting is a dead toggle — selecting it silently does nothing** — Settings UI exposes `cost_basis_method` (`components/settings/tabs/GeneralTab.tsx:196-212`), the backend validates and persists it (`routes/settings.js:118,144-147`), and full FIFO/LIFO implementations exist (`utils/portfolioMath.js:197-357` incl. dispatcher `calculateCostBasisByMethod`) — but **nothing calls them**. Both consumers hard-call weighted-average: `services/portfolio/portfolioSummaryService.js:161` and `hooks/portfolio/usePortfolioSummaries.ts:91`. A user who selects FIFO sees weighted-avg realized gains everywhere (incl. tax-relevant report figures). **Fix:** read the setting in `portfolioSummaryService` (and the report/tax fetchers) and call `calculateCostBasisByMethod(txns, method)`; thread `settingsStore.costBasisMethod` into the frontend hook; add a parity test per method. Alternatively, remove the setting + dead code — but the FIFO/LIFO code is complete and tested, so wiring it is the better path. ✅ 2026-06-11
- [x] ⏫ **[R7-6] FE/BE drift: frontend `totalInvested` uses `.abs()`, backend deliberately clamps at 0** — `hooks/portfolio/usePortfolioSummaries.ts:157` returns `toNumber(totalInvested.abs())`; the backend replaced exactly this with a 0-clamp and documents why: `portfolioSummaryService.js:226-230` *"Clamp at 0 rather than abs(): … abs() silently flipped that to a positive 'invested' figure"*. A fixed-income/real-estate position with more withdrawn than deposited shows **positive** invested capital in frontend-computed cards while backend endpoints report 0. **Fix:** mirror the clamp (`totalInvested.gt(0) ? totalInvested : ZERO`) in the hook; add this to the FE/BE parity test suite. ✅ 2026-06-11
- [x] ⏫ **[R7-7] Frontend `buildSummary` does no currency conversion — multi-currency portfolios sum mixed currencies** — `usePortfolioSummaries.ts` sums raw `txn.amount` values and `inv.current_price` (both in each investment's native currency) straight into `summaries` and `totals` (lines 39-74, 100, 208-216). The backend equivalent explicitly pre-converts *every* figure to the target currency (`portfolioSummaryService.js:81,225-242`). With, e.g., USD crypto + EUR ETFs, the frontend-computed per-class pages and totals add USD to EUR 1:1. **Fix:** either (a) fetch the rate map once (the API already exposes rates) and convert in `buildSummary`, or (b) stop client-side summary math for totals and consume `/portfolio-summary` (see R7-13). ✅ 2026-06-11
- [x] 🔼 **[R7-8] Two spike-sanitizers in `portfolioMath.js` have already drifted apart** — `sanitizeIsolatedValueSpikes` (lines 29-56: needle detection requires `bridgeLooksNormal`, result rounded to cents, single field) vs `sanitizeSnapshotSpikes` (lines 562-614: needle detection **without** the bridge guard, no rounding, also smooths the per-class value fields). Same concept, different thresholds: the snapshot pipeline (`snapshotBuilder.js:503`) and the route layer (`routes/info/_performanceHelpers.js:64`) therefore smooth *differently*, so a needle can survive one path and not the other — visible as chart/value mismatches between net-worth and performance views. Also the file's `toYmd` JSDoc (lines 15-23) is stranded above the wrong function. **Fix:** merge into one parameterized implementation (fields list + options), reattach the JSDoc, and pick one needle rule (the `bridgeLooksNormal`-guarded one is stricter and safer against smoothing real repricings). ✅ 2026-06-11
- [x] ⏬ **[R7-9] Loan schedule charges a full month's interest on a partial first month** — `services/calculations/loanSchedule.js:113-134`: when the loan starts mid-month and the first due date lands in the same month (start 06-05, payment day 20), installment 1 still charges `remaining × monthlyRate` for a full month. Standard simplification, but worth a code comment + doc note in the loan feature spec so it isn't re-reported as a bug. ✅ 2026-06-11

### Correctness — Belgian tax estimator (frontend lib)

- [x] 🔼 **[R7-10] Union dues and medical expenses deducted from the taxable base — not how Belgian PIT works** — `lib/belgianTax/pit.ts:360-369`: `unionDues` and `medicalExpenses` are subtracted from taxable income unconditionally, *on top of* the lump-sum professional-expense forfait. In Belgian PIT there is no general medical-expense deduction, and union dues are only deductible as part of **actual** professional expenses (mutually exclusive with the forfait). As written the estimator understates tax for anyone filling those fields. **Fix:** fold union dues into the `actual` branch of `computeProfessionalExpenses` only; remove the medical deduction (or clearly mark both as non-statutory approximations in the header's limitations list, which currently doesn't mention them). Verify against a current PwC/Fisconet source when implementing. ✅ 2026-06-11
- [x] 🔽 **[R7-11] Group-insurance tax credit has no cap** — `pit.ts:418-420` multiplies employee group-insurance contributions by 30% with no statutory ceiling, and the limitation isn't listed in the header. Add the cap to the year table or document the gap. ✅ 2026-06-11

## Electron shell follow-ups

- [ ] 🔼 **Crash-recovery port walk strands the shell on the error page** — `packaging/electron/main.js` (`findFreePort` + `composeStartOrUp`). If a previous session exits without the quit→`compose stop` path (crash, force-quit, `app.exit`), the containers stay up and keep publishing host port 3002. On the next launch `findFreePort(3002)` can't bind (docker-proxy holds it), walks to 3003, and health-polls a port the running container never publishes → "taking longer than expected" + error page even though the backend is healthy on 3002.
